Last-Write-Wins Reconciliation

For each external entity in the GET response, the engine answers two questions: do we already know it? and if so, who moved last?

TL;DR — operational
  • Mapped compare local vs external UpdatedAt against the snapshot taken at last sync
  • Tie on UpdatedAt always goes to the external (the server is authoritative for its timestamps)
  • Unmapped + parseable source_id adopts the local — does not duplicate
  • Unmapped + no match creates a new local + new mapping (CASE C)

§03 Why tie goes to external

The rule is external.UpdatedAt >= local.UpdatedAt — not >. The asymmetry matters in the rare equal-millisecond case. Three reasons:

The server generates its own timestamps

External updated_at is set by the server at write-receipt time. The client only observes it; it never produces it. Treating the server-side stamp as authoritative under tie matches the data-flow direction.

The local change is recoverable; the remote one is not

If the user re-edits the local after losing a tie, the next push propagates the new state. If we lost the remote change instead, the server has no concept of "the local that was about to win" — the divergence sticks until somebody notices.

Symmetric for items and lists

The same >= rule is applied for TodoListItem and TodoList. Documented in NOTES.md Assumptions — keeping the rule symmetric across entity types eliminates a class of "wait, but for items it's different" footguns.
