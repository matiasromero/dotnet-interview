SignalR over Outbox

Server-push, not request/response. How a CRUD on the REST API turns into a live UI update on every connected client — and why the broadcaster never touches ProcessedAt.

TL;DR — operational
  • TodoSyncHub typed server-push hub mounted at /hubs/todosync
  • ChangeNotification lightweight record: EventId, EntityType, EntityId, Operation, OccurredAt
  • OutboxBroadcaster reads OutboxEvents by cursor, maps to ChangeNotification, invokes the hub
  • OutboxBroadcastService BackgroundService that ticks every RealtimeOptions.BroadcastInterval (default 2s)

§01 The 3 actors at a glance

Three pieces, three different jobs. The hub is the channel; the broadcaster is the pure logic that knows what to send; the hosted service is the timer that keeps asking the broadcaster to do its work.

§02 Where the event is born

A REST CRUD lands on TodoListsController or TodoListItemsController, the matching service mutates the entity and persists it, then writes an OutboxEvent in the same flow (the entity save and the event save use separate SaveChangesAsync calls on purpose — Slice 6 covers the gap with a Phase B fallback). The full lifecycle of the outbox row — push to the external, mark ProcessedAt, retention purge — is the topic of outbox-syncmapping-flow.html.

For this story the only thing that matters is: a fresh row with a brand-new EventId just landed in the table, with ProcessedAt = NULL. From here on, two consumers race for it — the sync engine on the server side and, separately, the broadcaster on the UI side.

§04 What the client actually does

The payload is intentionally just metadata — no entity state. The client uses the EntityType + EntityId to decide which REST endpoint to hit; the full state arrives via that follow-up GET. Two reasons for this split: no payload duplication between SignalR and REST, and no shape coupling between the hub contract and the entity contract (the entity DTO can evolve without bumping the notification record).

// frontend (TypeScript) connection.on("TodoListChanged", (n: ChangeNotification) => { // payload is metadata only — fetch fresh state from REST refetch(`/api/todolists/${n.entityId}`); }); connection.on("TodoListItemChanged", (n: ChangeNotification) => { // notification carries no parent id — local cache already knows the parent invalidateItemCache(n.entityId); });

[note] The EventId is monotonically increasing per process, which the client can use as a dedupe key after a reconnect: anything with EventId <= lastSeen can be ignored. Documented as the versioning contract on ChangeNotification itself.

§05 Why the broadcaster never touches ProcessedAt

The same OutboxEvents table feeds two independent consumers. Each one tracks its own progress, and they never write to each other's column. That's what makes them safe to evolve separately.

OutboxBroadcaster
"UI fan-out"
Tracksin-memory cursor (max Id seen)
Restartcursor = MAX(Id) at startup → no historical replay
Writes DBnothing
Failurere-broadcasts on next tick (clients dedupe by EventId)
Sync engine (push/pull)
"external propagation"
TracksProcessedAt column on the row
Restartresumes from oldest WHERE ProcessedAt IS NULL
Writes DBProcessedAt = UtcNow on success
Cleanupretention purge by ProcessedAt + age (Slice 7)

Two consumers of the same log, each with its own advance mechanism, never stepping on each other. The broadcaster's only persistent footprint is a process-local long; everything else is read-only against a table the sync engine owns.
