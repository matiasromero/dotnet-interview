OutboxEvent vs SyncMapping

Two tables, two different questions. Here is the why — and how they relate inside a sync tick.

TL;DR — operational
  • OutboxEvent what changed locally that still needs to propagate (transient queue)
  • SyncMapping who is who between local and external (persistent correlation)
  • SyncRun how the engine fared in this tick (worker audit log)

§01 The 3 entities at a glance

Each entity answers a different question and lives a different lifecycle. The confusion arises because they share an IdempotencyKey column — but the roles are different.

OutboxEvent
"what changed"
Questionwhat to propagate to the external
Lifecyclecreated → processed → retention
CardinalityN rows per entity (1 per change)
Read bypush Phase A, oldest-first
SyncMapping
"who is who"
Questionwhich local ↔ which external
Lifecyclecreated on first sync, lives with the entity
Cardinality1 row per entity
Read bypush, pull, outbox dispatch
SyncRun
"how we did"
Questionwhat the engine did in this tick
Lifecycleopened at the start, closed at the end
Cardinality4 rows per tick (push/pull × list/item)
Read byno one at runtime · telemetry only

§03 Why IdempotencyKey appears in both

Both entities have an IdempotencyKey column and it is not accidental redundancy — but it is not clean design either. It is historical debt.

In the OutboxEvent, the key is generated once, at the moment the user does their CRUD. It travels as an HTTP header to the external:

// TodoListService.CreateAsync · slice 6 _context.OutboxEvents.Add(new OutboxEvent { EntityType = SyncEntityType.TodoList, EntityId = todoList.Id, Operation = OutboxOperation.Create, IdempotencyKey = Guid.NewGuid(), // ← GUID_X is born here OccurredAt = DateTime.UtcNow, }); // later, in the push tick: // POST /api/todolists with header "Idempotency-Key: {GUID_X}"

If the push retries (timeout, crash, Polly retry), the same GUID is reused → the external server deduplicates → no duplicate. At-least-once delivery + idempotency on the server = effectively exactly-once.

In the SyncMapping, the key is propagated from the event that created the mapping. It is audit trail ("this mapping was born from this event"). Functionally redundant today.

[note] The column on SyncMapping was added in slice 2, before the outbox, when the key was generated per-push-attempt. Slice 6 changed the model: now the key lives on the event. The mapping column was kept for compatibility with legacy Phase B. When Phase B is deprecated (slice 8 candidate), it becomes dead code.

§04 Why not merge them?

The natural question is: couldn't we put everything into SyncMapping with one extra field? No, and for three reasons that compound.

Different consumers

SyncMapping is read by push (anti-join), pull (LWW reconcile), outbox dispatch. OutboxEvent only by push Phase A. SyncRun only by telemetry.

Incompatible lifecycles

Mapping lives with the entity (years). Event lives hours or days until retention cleanup. Run lives one tick. Putting them together breaks query and retention patterns.

Different indexes and queries

Mapping looks up by (EntityType, LocalId). Outbox drains by OccurredAt WHERE ProcessedAt IS NULL (filtered index). Run groups by StartedAt. Each one with its best index.
